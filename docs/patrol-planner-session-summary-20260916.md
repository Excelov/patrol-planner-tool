**市政单位 / 燃气运营公司**（Q1=a）

1. **优先支持 GIS 数据库导入**（Shapefile / GeoJSON / 未来扩展 GeoPackage / PostGIS）

- **核心价值链**：DXF/GIS 数据 → 拓扑合并 → 路线规划 → 现场可用的巡检方案

## 三、用户原话反馈（需求核心）

> **1. "DXF图纸导入的管线不连续；底层应该是一图层连续的管道管线，这是之前系统没有做完善的地方"**

→ **根因**：DXF导出时被切成 N 个独立 LINE 实体，导入后没做拓扑连接。

→ **业务期望**：同一图层里管道是连续的，能识别出"主干管+支管"的网络结构，而不是一堆碎片。

> **2. "综合评估后期拿到别的 DXF，能直接导入；这是软件应该具备的能力；在地图加载；用于后期路线规划"**

→ **应用级诉求**：把 DXF 导入做成系统能力，不是一次性脚本。

> **3. "GIS数据 vs DXF 导入——考虑适用性、复杂程度、是否可商用"**

→ **产品决策结论**（已确认）：
- 当前阶段 DXF 是入门（数据易得，无运营属性）
- 未来必须 GIS 数据库（档案级、有法律地位、客户认）
- 数据层抽象：DXF/GIS/Shapefile 走同一管线入口 → **未来加新格式是增量的不是返工**
- 属性预留：`diameter_mm / pressure_level / material / installed_year` 等字段

> **4. "步骤二的地图重绘，效果几乎看不到"**

→ **实际效果问题**：合并视觉差异不明显 + 坐标偏

## 四、待解决问题（按紧急度排序）

### 🔴 P0：本次合并功能实测问题
- **症状**：用户导入 `dxf_pipeline_display_lines.geojson`，点"合并碎片管线"按钮，地图重绘后**视觉差异不明显**
- **症状2**：合并后**坐标偏了**，与之前系统处理的匹配性不好
- **初步诊断**：
  1. 合并算法本身工作（curl 测试 4848 段 → 1141 + 1253）
  2. 视觉差异小可能是因为：(a) 大量孤段本身就连不上；(b) 真正独立的管段不该被合并
  3. 坐标偏可能因为：**用户导入时默认选了第一个选项 `WGS84`，导致 `toGcj()` 又加了一次 GCJ-02 偏移**（关键怀疑点）

### 🟡 P1：当前功能完善
- 排查合并功能的 UI/UX 问题，确认是否需要：
  - 合并后用不同颜色显示"合并段" vs "孤段" vs "未合并前"
  - 默认坐标系选择改为 GCJ-02（推荐）
  - 阈值默认值是否需要调整

### 🟢 P2：DXF 直传端点
- 当前只支持 GeoJSON 导入后合并
- DXF 直接上传需要 ezdxf + pyproj 依赖、文件上传处理、临时存储路径
- **优先级低**——能用现有 GeoJSON 转换脚本走通就行

### 🟢 P3：GIS 数据库导入
- Shapefile (.shp + .dbf) 解析
- GeoPackage (.gpkg) 解析
- 字段映射（管径/压力级/材质/埋深）
- **Q3 优先级**：商业化前完成

### 🟢 P4：多管类支持
- 水 / 电 / 热力 / 燃气 通用图层
- 不同管类的颜色 / 图例 / 阈值
- **Q3 优先级**：商业化前完成

## 五、技术约束与设计原则（已确立）

### 5.1 数据层抽象原则
- 所有管线数据走同一入口（DXF / GIS / Shapefile 都通过 `pipeline_merge.py` 处理）
- 属性透传：合并时保留第一条的 `properties` + 添加 `source_segment_count / closed / merge_state`
- 阈值可调：端点合并距离默认 0.5m（适合 CGCS2000），范围 0.01–50m
- ponytail: O(n²) 端点匹配，n<2000 够用；>5000 升级 R-tree

### 5.2 坐标系约定
- **存储**：CGCS2000 经纬度（数据库 / CSV）
- **展示**：GCJ-02（高德地图）
- **计算**：GCJ-02 局部平面近似（覆盖分析）
- **导出**：GeoJSON 用 GCJ-02 近似反算 WGS84，附转换说明
- **坐标契约详见** `patrol-planner-development-plan.md` §3

### 5.3 不做什么（明确边界）
- ❌ 不做完整 CAD 拓扑清洗器（曲线、块引用、重复管段需另行检查）
- ❌ 不做测绘级 CGCS2000 分析（首版是规划估算）
- ❌ 不判断道路左右侧、隔离带、管线遮挡
- ❌ 不静默舍弃必巡管段（首版按普通机动车，超限提示）
- ❌ 不接入无人车核准路段（需要独立数据支持）

### 5.4 业务反馈口径
- 覆盖按管线长度加权，每 ≤20m 取样计算至道路折线的距离
- 重复驶过不重复累计
- 几何邻近覆盖 ≠ 实测检漏覆盖（设备探测方向、遮挡、车速、风向等条件尚未纳入）

## 十、区域全覆盖巡线新增需求（2026-09-15）

用户明确：市政管道巡线不能只按少量起终点或人工途经点规划。应先在地图上绘制多边形区域，将区域内及与边界相交的全部管线作为必巡目标；再依据 DXF/GIS 中的市政道路关联生成车辆行驶候选路线。路线允许往返和重复道路里程，但必须报告目标管段覆盖率、未覆盖段、不可达段和待人工核验段。

本轮已加入：

- 地图多边形选区模式，完成区域后自动筛选管线；区域数据随草稿保存和恢复。
- 区域筛选几何测试：点内外、穿越、完全外部和边界线。
- 开发计划中新增“区域全覆盖”要求及路线规则说明。

当前仍需下一阶段实现：将选中管段真正匹配到道路网络和行驶方向，生成超过高德单次 16 个途经点限制时的分段巡线任务；不能把管线中心线直接当作车辆路线，也不能把几何邻近覆盖直接当成实际检测覆盖。

## 十一、覆盖导向草稿点更新（2026-09-15）

“沿所选管线生成草稿点”已从原来的空间分散抽点改为覆盖导向贪心：按每条目标管线的端点和长度采样候选，逐点比较新增的长度加权几何覆盖，直到估算覆盖达到 95% 或达到途经点上限。界面显示估算覆盖率、未覆盖管段数量，并明确提示需要把点拖到实际可行驶道路。

首版不计算真实右转次数。右转优先和畅行性必须在下一阶段引入道路中心线、车道方向、单行和掉头成本后计算；当前直线点序不能替代道路转向分析。
